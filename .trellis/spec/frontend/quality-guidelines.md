# Quality Guidelines

> Code quality standards for frontend development.

---

## Overview

Project tooling is executed through `mise`, which pins the Node.js and pnpm versions in `mise.toml`. Development instructions should use `mise run <task>` rather than relying on whichever Node/pnpm happen to be installed globally.

The current quality stack is:

- Prettier for formatting.
- Oxlint for source/config linting.
- `tsc -b` for authoritative TypeScript checking.
- Vitest + Testing Library for DOM/integration tests.
- Playwright for browser smoke/E2E tests.
- Vite production build as part of the local quality gate.

Trellis-managed/generated files (`.trellis/`, `.agents/`, and `AGENTS.md`) are excluded from the project's Prettier pass. They are maintained by Trellis and may be regenerated by `trellis update`; project formatting must not rewrite them as a side effect of normal frontend checks.

---

## Required Development Entry Points

Use the tasks declared in `mise.toml`:

```bash
mise run dev
mise run build
mise run test
mise run lint
mise run typecheck
mise run check
mise run e2e
```

`mise.toml` currently pins:

```toml
[tools]
node = "24.19.0"
pnpm = "11.21.0"
```

Do not document `pnpm run ...` as the normal project workflow. The package manager remains an implementation detail beneath mise tasks.

---

## Forbidden Patterns

- Do not bypass `mise` for normal development commands when a mise task exists.
- Do not suppress TypeScript errors with `any` or broad assertions.
- Do not put E2E specs into the Vitest test glob; Vitest and Playwright suites are intentionally separated.
- Do not rely solely on visual/manual verification for user-visible interaction changes when an automated test can cover the behavior.
- Do not make interactive UI with non-semantic click targets when native HTML provides the behavior/accessibility.
- Do not let third-party Live2D/Cubism runtime types leak through the application boundary.

---

## Required Patterns

- Keep formatting clean with Prettier.
- Keep Oxlint at zero warnings/errors for touched code.
- Keep `tsc -b` green.
- Run `mise run check` before considering normal frontend work complete.
- Run `mise run e2e` when changes affect navigation, browser-only behavior, or a user-visible interaction covered by Playwright.
- Add or update automated tests when changing observable behavior.
- Preserve accessibility semantics and names used by tests unless the product behavior intentionally changes.

The current aggregate local gate in `mise.toml` is:

```toml
[tasks.check]
run = [
  { task = "format-check" },
  { task = "lint" },
  { task = "test" },
  { task = "build" },
]
```

## Testing Requirements

### Vitest + Testing Library

Use for React behavior that can be verified in the DOM without needing a real browser/GPU.

Current reference: `tests/HomePage.test.tsx` verifies the fan-project identity and click interaction through accessible queries:

```tsx
const puppet = screen.getByRole('button', {
  name: '与开发中的花谱 2D 角色互动',
});

await user.click(puppet);

expect(screen.getByText('01 SIGNALS')).toBeInTheDocument();
```

Prefer role/name queries over class selectors or implementation details.

### Playwright

Use for browser-level smoke behavior, routing, and interactions whose environment matters.

Current reference: `tests/e2e/home.spec.ts` loads `/`, verifies the page heading and interactive puppet, clicks it, and verifies the resulting signal count.

### Live2D/runtime testing boundary

The future Cubism runtime should be testable through `Live2DAdapter`. Most application tests should verify calls/behavior at that boundary; keep true WebGL/model smoke tests narrow to avoid flaky GPU-specific assertions.

---

## Accessibility Quality

- Keep semantic controls and labels intact.
- Test important interactive controls through accessible roles/names.
- Decorative elements must not pollute the accessibility tree.
- Dynamic, non-critical status updates should use an appropriate live region when users need them announced.
- Respect reduced-motion behavior in visual/animation work when applicable.

---

## Code Review Checklist

- Does the change belong in `app`, `pages`, `features`, or global `styles` according to current ownership?
- Is feature-specific CSS colocated in a CSS Module instead of becoming global CSS?
- Are existing CSS custom-property tokens reused where appropriate?
- Does React own UI state while imperative renderer/runtime state remains outside React state?
- Are props/types narrow and explicit?
- Are user interactions semantic and keyboard accessible?
- Were affected tests added or updated?
- Does `mise run check` pass?
- If browser behavior changed, does `mise run e2e` pass?
